# AGENTS.md

Правила для всех агентов этого репозитория. Прочитайте этот файл первым: он задаёт карту проекта.

Spec-Driven Company (SDC) в одной строке: истина живёт в письменных требованиях, агенты исполняют их, а состояние видно без вопросов к людям.

## До начала: определите тип задачи

Каждая задача относится к одному из трёх типов. Определите его до чтения файлов и работы с Git.

1. **Разговор.** Объяснить, обсудить, посоветовать. Git не трогать.
2. **Чтение.** Прочитать файлы, ничего не менять. Сначала обновить `main`, затем читать.
3. **Запись.** Любое действие, которое может изменить репозиторий, включая одну строку документации. Предварительная проверка, отдельная ветка, никаких записей в `main`.

## Где живёт истина

- `docs/README.md` — одна страница: что это за проект, какие решения приняты, где что лежит.
- `docs/journal.md` — решения и причины: что решили, что отвергли, чьими словами. Только добавление записей, новые сверху.
- `docs/<zone>.md` — канон одной зоны: как она работает сейчас. Одно правило записывается один раз и меняется заменой.

Файлы конкретных сред лежат рядом с этим файлом и дополняют, но не ослабляют его: `CLAUDE.md` направляет Claude Code сюда, `CODEX.md` содержит специфику Codex. При разногласиях этот файл старше.

Пара файлов в корне `docs/` относится ко всему проекту. Каждая подпапка `docs/` содержит свою пару: `README.md` — краткое описание папки, `journal.md` — рассуждения, которые к нему привели. Новая папка создаётся сразу с обоими файлами. Файл зоны появляется с первым правилом зоны; пустые файлы не создавать.

Если правило не записано по определённому адресу, его не существует. «Спроси того, кто помнит» — не адрес.

Три вида истины, три дома. Смысловые решения — что строим, для кого, каким голосом — живут в `docs/`. Технические соглашения — линтер, форматтер, версии — живут в конфигурации; не копируйте их в документацию. Живые данные и статусы — пользователи, заказы, состояния датчиков — живут в базе; документы описывают устройство, а не текущие значения.

## Как работать

1. **Работать в отдельной ветке или worktree.** Напрямую в `main` ничего не записывается. Изменения попадают в `main` через pull request.
2. **Нет задачи без критерия готовности.** Если нельзя проверить, что задача выполнена, спросить. Не начинать.
3. **Спецификация до кода.** Требования, план и дизайн — в одном документе до первой строки кода.
4. **Канон до кода.** Правило сначала меняется в `docs/`, затем в коде и тестах, в том же изменении. Никакого «сейчас код, документация потом».
5. **Тесты удерживают правила.** Правило, которое уже стоило времени или денег, получает тест. Сломанный тест исправляется до слова «готово».
6. **В зонах риска подготовить, но не выполнять.** См. таблицу ниже. Кнопку нажимает человек.
7. **Сообщать результат, а не усилия.** Сказать, что сделано, что не сделано и что не удалось проверить.

## Git

- Репозитория ещё нет? Выполнить `git init`, закоммитить настройку в `main` и сообщить об этом в отчёте. Это единственная прямая запись в `main` за жизнь проекта. Remote и pull request появляются с первым кодом.
- Предварительная проверка каждой задачи с записью: `git status`, `git fetch`, обновление `main` без слияния, затем новая ветка от свежего `main`. Если `main` содержит незакоммиченные изменения или опережает origin, остановиться и сообщить об этом.
- Имя ветки: `<agent>-<YYYY-MM-DD>-<topic>`, например `codex-2026-09-02-signup-form` или `claude-2026-09-02-signup-form`.
- Коммитить каждый целостный шаг. Коммит — точка возврата. В него входят только изменения этой задачи; никогда секреты и чужая незавершённая работа.
- Отправить ветку и открыть pull request. Код всегда проходит через pull request. Изменение только `docs/` и этого файла можно влить в `main` напрямую, если `docs/README.md` не говорит обратного.
- После слияния: обновить `main`, удалить ветку и worktree.

## Стек

Из чего состоит проект и две команды, нужные каждому агенту. Заполняется при настройке, меняется заменой при смене стека. Кода ещё нет? Написать «пока нет» во всех трёх строках; не выдумывать проверку для проекта, в котором нечего проверять.

- Состав: Node.js LTS, pnpm, TypeScript, Next.js с App Router, React, Tailwind CSS; Convex для базы и серверных функций; Vitest, ESLint и Prettier; будущий хостинг — Vercel.
- Проверка: `pnpm check` — форматирование, линтер, генерация типов маршрутов, проверка типов и тесты.
- Запуск: `pnpm dev` → http://localhost:3000; страница управления — http://localhost:3000/admin.

## Проверка

Запускать команду проверки из раздела «Стек» перед каждым коммитом. Красный результат означает, что задача не закончена, независимо от причины. Предупреждение, которое уже было, не повод звать человека.

## Зоны риска: подготовить, но не выполнять

| Всегда | Сначала спросить | Никогда |
|---|---|---|
| работать в ветке, писать спецификацию, запускать проверку, сообщать результат | всё, что перемещает деньги, затрагивает ключи или доступы, хранит или отправляет персональные данные, публикует за пределами репозитория, меняет настройки production | удалять данные, переписывать чужие изменения, делать force-push в `main`, помещать секреты в файлы или логи |

«Сначала спросить» означает: сделать всё до нажатия кнопки, затем остановиться и передать человеку одну строку с выбором. Не начинать обсуждение посреди работы.

## Решения

Решение — выбор, который можно переоткрыть завтра. Он записывается в `docs/journal.md` отдельной записью со стабильным именем:

```
## 2026-09-02 15:01 · <agent> · ⚖️ signup-without-password · Вход только по ссылке из письма

**Решение.** ...
**Отвергли.** ... и почему.
**Слова владельца.** «...»
```

«Слова владельца» — цитата человека. Если задача пришла как вставленный промпт без дополнительных слов человека, процитировать первое предложение промпта.

Правила решений:

- У каждого правила один дом. Остальные документы ссылаются на него, а не копируют.
- Канон меняется заменой. Старое правило удаляется в том же коммите; история живёт в журнале и Git.
- Перед предложением изменить архитектуру, URL, схему данных или процесс прочитать журнал этой зоны. Решённые вопросы не переоткрываются без запроса владельца.
- Рассуждения из чата, не попавшие в журнал, — незавершённая работа, как код без коммита.

Если обнаружено нарушение письменного правила, сначала исправить причину, затем симптом, сверху вниз: правило не записано — записать; записано не там — перенести; записано, но никто не нашёл — сделать находимым от точки начала задачи. «Буду внимательнее» — не исправление.

## Структура

Семь — сигнал, а не цель. Меньше сущностей лучше; уровень должен читаться одним взглядом. Когда на одном уровне появляется восьмой файл, папка, таблица, переменная или скрипт, поднять вопрос группировки; группировать по смыслу, а не ради числа. Два файла одной природы на одном уровне — ранний сигнал: спросить, не нужна ли им папка с `README.md`.

`docs/README.md` остаётся в пределах одной страницы. Если разрастается, одной из тем нужна собственная папка.

## Production

Всё, что работает без человека — форма, вебхук, задача по расписанию, интеграция, новый источник данных — появляется с четырьмя вещами в одном изменении:

1. сам элемент;
2. его канон в `docs/`: откуда вход, куда пишет, известные ограничения;
3. его стекло: место, где видно состояние, страница или строка на существующей странице;
4. его иммунитет: внешняя проверка, которая явно падает при поломке элемента («форма отображается, адрес отвечает 200»), а не бизнес-метрика.

Контент и вёрстка без нового потока данных или денег находятся вне этого правила.

## Отчёт

Каждая задача с записью заканчивается одинаковым блоком, чтобы человек прочитал его за десять секунд:

```
---
Результат: влито | pull request открыт | закоммичено (только первая настройка) | заблокировано
Ссылка: <pull request или коммит>
Файлы: <путь> +a/-b, по одному на строку
Не проверено: <что не удалось проверить и почему> или «ничего»
Далее: один шаг, который сильнее всего двигает проект, и почему
```

## Цикл

задача словами → работа → приёмка по критерию → выпуск → наблюдение → следующая задача

Каждая единица работы — полный оборот этого цикла. Один и тот же цикл действует на каждом масштабе: функция, продукт, бизнес-зона, компания. Наблюдение за последним оборотом даёт следующую задачу.
