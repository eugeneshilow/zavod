## 2026-09-20 20:53 · claude-opus-5 · ⚖️ story-rail · Третья рельса роликов: закадровый голос, кадр под фразу, слово на экране

**Решили.** У роликов появляется третья рельса — «История»: один файл `content/reels/stories/<id>.json`, закадровый голос читает историю, картинка меняется под каждую фразу, на экране по одному слову в такт речи. Лица в кадре нет. Форма снята с донора «Новостной Гусь» целиком (срез `docs/research/2026-09-20-gus-formula/README.md`): заголовок-загадка, первая фраза сразу с героем и ситуацией, тело — механика «почему так» с поворотом, финал — последствие или ирония, ни одного призыва. Сборка: голос одним куском (`say -v Milena -r 170` для черновика, SpeechKit для чистовика), `whisper-cli -ml 1 -sow` даёт время каждого слова, биты получают границы по доле слов, каждый `visual` рендерится в клип своей длительности, клипы идут встык, субтитры — `.ass` по одному слову, водяной знак `vibecoding.ru` под ними. Четыре вида кадра: картинка с наездом, кусок видео с кропом, типографская карточка с цифрой и карточка поста, нарисованная нами. Каждый файл медиа несёт строку в `content/reels/media/LICENSES.md`; файл без строки в ролик не идёт. Канон зоны — `docs/reels.md`, раздел «История». Первый ролик — `robot-knife` по бенчмарку RoboHarm и посту Илона Маска.

**Отвергли.** Говорящую голову и аватар — у донора их нет вовсе, а 1,67 млрд просмотров есть; ⚖️ virtual-presenter остаётся возможной ставкой на другую форму, не на эту. Кроссфейды между кадрами, как в рельсе серии, — донор режет встык, и на темпе «кадр каждые две секунды» плавный переход съедает сам кадр. Чужие кадры из фильмов и мемы без лицензии — у донора это обычная практика ленты, для компании риск; вместо них свои карточки, свободные фото и кадр источника новости с указанием автора.

**Слова владельца.** «И давай за основу для ролика возьмем https://x.com/elonmusk/status/2101324271712657470 запускай стройку»

## 2026-09-20 17:21 · claude-opus-5 · ⚖️ telegram-door · Вторая дверь публикации: тот же ролик едет ещё и в канал Telegram

**Решили.** У очереди публикации теперь две двери: Instagram и Telegram. Очередь остаётся одна (`data_cooked_instagram_reels`), у строки появилось поле `channel`; поля нет — значит `instagram`, поэтому старые строки читаются без миграции, а индекс `by_channel_status_scheduled` их не видит, и человек один раз проставляет им дверь командой `backfillChannel`. Один файл заливается в хранилище один раз и встаёт двумя строками с общим плановым временем: `node scripts/reels/publish.mjs <файл> "подпись"` по умолчанию кладёт материал в обе двери, `--to telegram` — только в одну. Тот же `storageId` второй раз в ту же дверь не встаёт, в другую — встаёт: это и есть кросспостинг. Один крон-тик `instagram-run-queue` обслуживает обе двери по очереди и публикует не больше одного материала на дверь; `INSTAGRAM_POSTING_ENABLED` остаётся общим рубильником (имя историческое), а тумблер в `ops_channel_toggles` у каждой двери свой и по умолчанию выключен. Telegram публикует Bot API одним запросом: ролик — `sendVideo` с `supports_streaming`, картинка — `sendPhoto`, файл Telegram выкачивает сам по адресу хранилища Convex. Ссылка на пост складывается как `https://t.me/<канал>/<номер сообщения>`. Канал — `t.me/autovibecoding`, бот — его администратор. Цифры по Telegram машина не собирает: Bot API их не отдаёт, и это записано краем канона, а не подразумевается. Канон зоны — `docs/publish.md`.

**Отвергли.** Три вещи. YouTube как дверь для бонусного урока — ролики, залитые через API непроверенным приложением, ложатся приватными до аудита Google, и урок про «машина публикует сама» превратился бы в урок про ожидание проверки. Отдельную таблицу очереди под Telegram — одна очередь даёт одно стекло: на `/admin` видно обе двери одной таблицей, а две таблицы пришлось бы сводить глазами. Токен Telegram в таблице, как у Instagram, — у Bot API он не протухает, продлевать нечего, поэтому ему хватает переменной окружения Convex.

**Слова владельца.** «По телеграму наверное надо сделать отдельный бонусный урок? … так а куда мы будем публиковать эти рилсы в телеге? В канал?» — и вердикт: «channel: t.me/autovibecoding, бот тоже».

## 2026-09-20 13:28 · claude · ⚖️ reels-rail-playwright-ffmpeg · Ролики собирают Playwright и ffmpeg, файл всегда со звуком

**Решили.** Вертикальные ролики 1080×1920 собираются в этом же репозитории двумя рельсами с общей концовкой: серия слайдов (`content/reels/series/*.json` + лекало `content/reels/template.html`) и плакат из одной картинки (`content/reels/posters/*.json`). Кадры снимает Playwright (chromium) по HTML-лекалу, склеивает ffmpeg: кроссфейд 0.35 с, 30 кадров в секунду, H.264 `crf 20`, `yuv420p`, `+faststart`. Тайминг живёт в одном месте — `scripts/reels/lib.mjs`, длительность серии считается формулой `3 + N×3.4 + 3 − (N+1)×0.35`, её держит тест. Звуковая дорожка обязательна всегда: с флагом `--music` вшивается royalty-free трек из `assets/music/` с затуханием 1.5 с, без флага пишется тишина, и рендер помечает ролик как черновик. Каждый трек получает строку в `assets/music/LICENSES.md`. Готовые файлы ложатся в `out/`, он вне git. Канон — `docs/reels.md`.

**Отвергли.** Remotion — самый зрелый инструмент для анимации кодом, но платный за порогом трёх человек ($100/мес для машины, которая рендерит по расписанию); Playwright и ffmpeg бесплатны и ставятся одной командой. Ролик без аудиодорожки — Instagram такой файл не принимает, поэтому «без музыки» реализовано тишиной, а не отсутствием дорожки. Рисовать текст плаката через `drawtext` ffmpeg — шрифт пришлось бы искать файлом на диске; тот же текст в CSS даёт единый запасной шрифт с лекалом слайдов. Вшивать музыку из библиотеки Instagram — её лицензия действует только внутри продуктов Meta.

**Слова владельца.** «Задача: рельса сборки вертикальных роликов (1080×1920, 9:16) из HTML-слайдов и из одной картинки, без человека, в этом же репозитории.»

## 2026-09-20 13:22 · claude · ⚖️ reels-straight-to-instagram · Ролики едут в Instagram сами, рельсой из autovibecoding

**Решили.** Полный цикл публикации короткого видео живёт внутри проекта, а не в руках человека. Готовый файл заливается в хранилище Convex и встаёт в очередь `data_cooked_instagram_reels`; крон раз в 30 минут забирает один созревший ролик и публикует его через Graph API v23 (контейнер REELS, ожидание обработки, `media_publish`); крон раз в 6 часов приносит обратно просмотры, охват и реакции; крон раз в сутки продлевает токен. Рельса перенесена почти дословно из проекта `vibecoding-ru` (`convex/services/instagram.ts`, таблицы `data_*_instagram_*`, `workflows/instagram_publishing.ts`) — это работающий каркас, снятый целиком, а не написанный заново. Перед публикацией сходятся четыре замка: `INSTAGRAM_CRONS_ENABLED`, `INSTAGRAM_POSTING_ENABLED`, тумблер канала (по умолчанию выключен) и живой токен с непустой суточной квотой. Токен живёт только в таблице `ops_instagram_state` и наружу не отдаётся ни одним запросом. Очередь везёт два вида материала: вертикальный ролик и одиночную картинку (поле `mediaType`, по умолчанию ролик) — у картинки в контейнере Graph API поле `image_url` и нет `media_type`, готовность опрашивается тем же поллингом. Статус видно на `/admin`: блок «Очередь Reels» и блок «Эфир», там же кнопка паузы канала. Иммунитет — `/api/reels/health` и почасовой сторож `reels-alive`. Канон зоны — `docs/publish.md`.

**Отвергли.** Три вещи. Публикацию руками по кнопке — владелец просил полный цикл, а не полуавтомат. Хранение токена в переменных окружения, как у остальных ключей, — токен живой, его продлевает крон, и переменная окружения такого не умеет. Публикацию с одной попытки: сеть моргнула — ролик пропал бы навсегда, поэтому первая и вторая неудача возвращают его в очередь со сдвигом на два часа, и только третья зажигает тревогу.

**Слова владельца.** «вези сразу всё в рилс — рельсы у нас уже есть внутри autovibecoding проекта, их перетащи в проект zavod-v6; делай сразу полный цикл — все ролики вези напрямую в инсту»; «кроме REELS нужна публикация обычного фото-поста»

## 2026-09-19 21:40 · claude · ⚖️ go-online-github-vercel-convex · Проект живёт онлайн: приватный GitHub, Vercel, Convex в облаке

**Решили.** Код — в приватном репозитории `eugeneshilow/zavod-v6`; в `main` только слиянием pull request, и на каждый pull request и push в `main` GitHub Actions гоняет ту же `pnpm check`, что и человек. Хостинг — Vercel, привязанный к репозиторию: push в `main` собирает продакшен, pull request — превью; в продакшене сборка `pnpm check && npx convex deploy --cmd 'pnpm build'`, на превью `pnpm build`. База — Convex в облаке, деплои dev и продакшен; ключ продакшен-деплоя `CONVEX_DEPLOY_KEY` кладёт человек в Vercel сам. Иммунитет — почасовой `prod-alive` по адресу из `PROD_URL`. Канон — `docs/deploy.md`. Что человек делает дальше: создаёт deploy key в Convex и кладёт в Vercel; после слияния проверяет адрес продакшена и `/admin`.

**Отвергли.** Локальный бэкенд Convex — продакшену на Vercel не к чему подключаться. Публичный репозиторий — проект приватный, пока владелец не решит иначе. Сборка без проверки ради скорости — `/admin` показывал бы пустое стекло там, где статус нужнее всего.

**Слова владельца.** «Отвечай на языке этого промпта. Настрой Spec-Driven Company в этой папке со стеком Next.js и Convex и выведи проект онлайн: приватный репозиторий на GitHub, Vercel и Convex в облаке.»
